# Case Study: ASIOD / Receipt-First Governance

## Problem

AI-assisted software delivery creates a specific reliability problem: an agent can report success even when the requested outcome has not actually been proved.

ASIOD is a governance pattern built around the opposite assumption. **Completion is an evidence state, not a sentence generated by an agent.**

## Architecture Approach

The pattern is receipt-first. Important work should leave enough evidence for a human or another agent to determine whether it really passed.

Core ideas:

- Evidence before completion claims
- Explicit PASS, BLOCKED, and FAIL states
- Receipts for important actions and build stages
- Canary checks for risky or unexpected behaviour
- Approval gates around sensitive operations
- Snapshot/rollback thinking before destructive change
- Separation of public evidence from credentials or private source code

## Why It Matters

This approach grew out of practical AI-assisted development where multiple agents, coding tools, repositories, and runtime environments can all disagree about what is actually live.

Receipt-first governance reduces the temptation to treat tool output as truth. The final acceptance question becomes: **what can we prove happened?**

## Public Evidence Policy

This portfolio intentionally does not publish secrets, internal infrastructure maps, credentials, or commercially sensitive source code. Where a current runtime receipt is not safe to publish, the case study describes the governance pattern rather than inventing a success result.
